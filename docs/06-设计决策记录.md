# 设计决策记录（ADR）

> 状态：Accepted（已采纳）/ Proposed（建议）  
> 日期：2026-08-19

## ADR-001：游戏工作名《魔王城》

- 状态：Proposed（工作名，未最终确定）
- 决策：采用「魔王城」（The Demon Lord's Keep）作为工作名。
- 理由：题材为魔王阵营；「魔王城」同时点出基地建设与防守核心。
- 备选：若用户有既定名称，以用户为准。

## ADR-002：单机先行，联机后置到 M4

- 状态：Accepted
- 决策：开发顺序为 M1 单机垂直切片 → M2 局内系统 → M3 基地 → M4 联机。
- 理由：核心乐趣（割草 FPS + 敌潮）必须先验证；联机在单机系统稳定后接入，避免双线返工。
- 代价：联机需求会影响早期数据结构，需在 M1 就遵守「服务器权威」的写法习惯。

## ADR-003：服务器权威 + 敌潮「批次快照 + 客户端同构重建」

- 状态：Accepted
- 决策：见 [future/04-联机方案.md](./future/04-联机方案.md) 第 4 节。
- 理由：全量复制不可行；Lockstep 不适合 FPS；混合方案平衡带宽、一致性与手感。
- 代价：客户端表现实体与服务器实体弱绑定，需要「注目实体精确同步」补偿。

## ADR-004：玩家档案与世界档案分离

- 状态：Accepted
- 决策：玩家 Meta 档案属个人（本地/Steam ID），基地世界档案属房主。
- 理由：任何玩家带自己的进度进入任何人的基地，联机社交成本最低；房主离线不影响他人档案。
- 代价：需要两套存档版本化与权限校验。

## ADR-005：单模块起步，按目录分区

- 状态：Accepted
- 决策：M0-M3 保持单模块 `GobulinGame`，按 Core/Combat/Player/Enemy/Horde/Base/Meta/Net/Data/UI/AI 分区；M4 后评估拆分独立模块。
- 理由：避免过早抽象；模块边界在系统成型后更清晰。
- 触发拆分信号：编译时间显著上升、依赖违反目录边界、需要独立测试/插件复用。

## ADR-006：自研轻量属性/Perk 系统，暂不引入 GAS

- 状态：Accepted（可复审，触发条件见下）
- 决策：v1 用 `UBattleAttributeComponent` 持有 `UBattleAttributeSet`，配合修改器和 GameplayTags；预留 GAS 接口。
- 理由：Perk 以静态加成与少量主动技为主；GAS 面向 Actor/AbilitySystemComponent，不适合覆盖千人 Mass 敌潮的伤害结算；GAS 复制/预测模型与我们的自定义快照联机叠加会增加复杂度。
- 复审时机：若 M2 主动技/状态效果复杂度显著上升，评估**只给玩家侧局部引入 GAS**（敌潮仍走 Mass 自研伤害）；属性读取走统一接口，便于迁移。

## ADR-007：数据驱动使用 DataAsset + DataTable + GameplayTags

- 状态：Accepted
- 决策：武器、敌人和战斗配置使用 DataAsset，批量内容再使用 DataTable；数值曲线使用 CurveAsset/CurveTable；状态和规则使用 GameplayTags。
- 理由：策划可调、联机校验容易、避免硬编码魔法数字。

## ADR-008：联机延迟补偿 MVP 不做完整回溯

- 状态：Accepted（可复审）
- 决策：MVP 用服务器收到时的位置 + 容差球判定；不做 Server Rewind。
- 理由：开发成本与手感收益的平衡；RTT ≤ 200ms 时足够。
- 复审时机：M4 实测若命中丢失感明显，再实现 100ms 回溯。

## ADR-009：Listen Server 优先，专用服务器发布前评估

- 状态：Accepted
- 决策：M4 联机用 Listen Server + Steam P2P；M6 前完成房主迁移或专用服务器。
- 理由：快速验证玩法；Dedicated Server 是发布期稳定性的必要项但不是玩法验证的必要项。

## ADR-010：美术采用 3D 场景 + 全 2D 纸片角色

- 状态：Accepted
- 决策：3D 低模场景 + 全 2D 纸片角色（勇者潮、NPC、BOSS 全 2D），暗黑童话手绘风；玩家手部武器用 2D FPS 武器贴图。
- 理由：美术成本低、对千人同屏性能友好、风格辨识度高；2D 纸片在 3D 场景中需用描边/剪影/假阴影保证可读性（见 TDD 5.5）。
- 风险：FPS 可读性与动画成本需在 M1 原型验证。

## ADR-011：死亡=转生 + 三资源 + 转生深度

- 状态：Accepted
- 决策：局内陨落不丢收益（转生叙事）；金币（局内）+ 魔核/冥银（永久）；转生头衔 + 转生深度 1-10 提供 NG+ 式难度。
- 理由：增量核心承诺「每次死亡都有意义」；转生让死亡无惩罚成为世界观设定。

## ADR-012：建造采用地块 + 蓝图配方，不做全自由搭建

- 状态：Accepted
- 决策：基地使用固定地块网格与配方建筑；不做自由网格/任意形状建造。
- 理由：大幅降低联机校验、寻路与美术成本；「防御决策」仍然存在（位置/类型/预算），但不会吞掉建造系统预算。

## ADR-013：引潮机制采用「发布悬赏」

- 状态：Accepted
- 决策：原「钟声」机制 1:1 迁移为「悬赏榜」：发布/追加悬赏 → 勇者潮增强 + 战利品倍率 + 魔核充能。
- 理由：与魔王阵营身份契合；悬赏有天然的叙事与 UI 载体（悬赏令/战鼓）；机制骨架不变。
- 代价：需要为悬赏制作张贴、战鼓与狂潮的专属表现。

## ADR-014：联机身份全员魔王（名号区分风格）

- 状态：Accepted
- 决策：所有玩家都是魔王，通过名号（剑渊魔王/焰狱魔王/永夜魔女/冥渊魔王）区分技能风格；不存在上下级叙事。
- 理由：合作对等、避免「房主=上级」的身份割裂；名号只影响技能风格，不影响数值框架。

## ADR-015：UI 底层采用 CommonUI

- 状态：Accepted
- 决策：启用 CommonUI 插件与 CommonInput 模块；交互型 UI（主菜单/大厅/悬赏榜/建造/结算）使用 CommonActivatableWidget / CommonButtonBase；战斗 HUD 使用普通 UMG。
- 理由：键鼠/手柄统一交互、输入绑定与焦点管理现成，且与 Enhanced Input 官方集成；不引入 Lyra 全栈。
- 代价：需要维护 UI 输入模式与玩法输入的切换，CommonUI 有一定的样板代码。

## ADR-016：2D 角色采用自研 Billboard Flipbook 管线（已被 ADR-020 替代）

- 状态：Superseded
- 决策：不用 PaperZD/Paper2D 作为核心方案；自研 `USpriteFlipbook`（图集资产）+ `USpriteBillboardComponent`（面向相机四边形）作为底层管线。正式敌人使用 `UGobulinEnemyDefinition` 配置各状态动画，由 `UGobulinEnemyAnimationComponent` 统一切换；杂兵规模化后再接 Mass 实例化。
- 理由：解决「3D 场景中的相机朝向」与「千级实例化」两个核心问题；避免第三方插件依赖与 UE 5.8 兼容性风险；图集帧动画契合纸片美术风格。
- 代价：帧播放、方向选择与 LOD 需要自研维护（复杂度可控）。
- 复审：若未来 NPC 演出需要骨骼级 2D 动画，再单独评估 Spine/PaperZD，不影响敌潮管线。
- 补充（2026-08-09）：角色分层——杂兵 1 方向面向相机；玩家/队友/NPC 用 8 方向帧（4 方向绘制 + 水平镜像）并按移动/瞄准切换朝向；BOSS 用 8 方向高帧；玩家阵营统一描边 + 名牌；第一人称武器用 2D 贴图层（见 ADR-018）。

## ADR-018：第一人称采用 Plane + 曲线的 2D 武器贴图层

- 状态：Accepted
- 决策：本地视角不把 3D 手臂 AnimBP 作为主线；使用相机挂载的 Plane 显示武器贴图，由 `UGobulinWeaponViewComponent` 管理表现，由 `UGobulinSwordCombatComponent` 推进攻击时间，并使用位置/旋转曲线驱动变换。
- 理由：与 2D 纸片美术同源；武器层仅本地可见、不参与复制；曲线可以在 Sequencer/曲线编辑器中直接调整，适合当前剑的单次攻击表现。
- 当前实现：`Sword.png`、`DA_Sword`、`IA_SwordAttack` 和 `IMC_Player` 已接入；剑尖轨迹、伤害结果、相机反馈和 Hit Stop 已完成基础闭环。

## ADR-019：正式敌人从 Demo 占位类重新建立

- 状态：Superseded（具体类与数据结构已被新的后端中立敌人地基替代）
- 保留结论：正式敌人不以旧 `ADemoEnemy` 作为生产基类。
- 新决策：见 ADR-020；当前 Actor 后端为 `AGobulinEnemyActor`，玩法状态归 `UGobulinEnemySubsystem`，数据定义为 `UGobulinEnemyArchetype`。

## ADR-020：Paper2D 作为敌人内容制作源，运行时保持后端中立

- 状态：Accepted
- 决策：Actor 原型使用原生 `UPaperFlipbook` 与 `UGobulinEnemyPresentationComponent`；身体和表现参数写入 `UGobulinEnemyArchetype`。使用编辑器专用 `AGobulinEnemyPreviewActor` 在关卡视口装配并通过白名单按钮烘焙，不直接把预览 Actor 用作运行时敌人。
- 理由：Flipbook 帧和帧率可由内容制作者直接微调；胶囊与纸片可以在同一视口对齐；运行时生成仍由 World Subsystem 管理，避免把关卡对象、Actor 指针或 Paper2D 组件写入战斗协议。
- Mass 边界：Paper2D 是内容制作源和当前 Actor 适配器，不承诺一实体一组件。Mass 后端将语义动画数据转换为共享 Fragment 与实例表现数据，继续复用句柄、状态、生成、伤害和事件协议。

## ADR-021：近战查询使用独立 CombatTrace 通道

- 状态：Accepted
- 决策：近战 Sweep 使用 `CombatTrace`；世界默认 Block，敌人胶囊显式 Overlap。Visibility 只承担可见性/视线语义。
- 理由：多目标近战查询需要穿过一个敌人继续收集后续目标，同时仍被墙体截断；这与 Visibility 和物理碰撞都不是同一个规则集。
- 注意：查询响应不依赖 `Generate Overlap Events`。新增或修改通道后需要重启编辑器。

## ADR-022：敌人决策与 Actor 导航执行器分离

- 状态：Accepted
- 决策：`UGobulinEnemySubsystem` 通过后端中立快照执行低频索敌并生成 `FEnemyMoveIntent`；当前 `AGobulinEnemyActor` 使用 ACharacter/CharacterMovement，`AGobulinEnemyAIController` 只执行 NavMesh 请求和回报结果。
- 理由：M1 需要成熟的地面、坡道和碰撞移动来验证战斗，同时不能把 Actor、Controller、Blackboard 或导航路径写入敌人运行时协议。
- 不采用：当前普通敌人不引入 Behavior Tree、Blackboard、AI Perception 或 StateTree。少量精英/BOSS 后续仍可使用 StateTree。
- Mass 边界：Mass 后端复用目标、移动意图、状态和事件语义，但用空间查询与 Processor 替换 ACharacter、AIController、RVO 和 NavMesh 路径跟随。

## ADR-023：基本敌人采用观察者相对四方向 Idle/Run 表现

- 状态：Accepted
- 决策：基本敌人 Archetype 要求四方向 `Idle`、四方向 `Run` 和一个 `Death`，合计九个 Flipbook。纸片始终水平面向本地观察者，四方向由敌人实际水平速度相对本地相机选择；静止时播放上一次有效方向的 Idle，Death 是否循环由 Archetype 配置。
- 理由：路径转弯和 RVO 避让会使实际速度偏离目标方向；按实际速度选择可以保持脚步与位移一致。四方向 Idle 能避免静止冻结在跑步中间帧，同时不把出生、攻击或受击动作提前纳入基本敌人必选资源。
- 当前资源：`EA_BasicEnemy` 使用 FieldPaladin 的 `Idle_D/U/L/R` 与 `Run_D/U/L/R`；`D/U/L/R` 分别映射为朝向观察者、远离观察者、屏幕左、屏幕右。死亡使用临时 `BattlePaladin__Downed` 占位资源。
- 稳定性：方向分界使用切换滞后；同一动作切换方向时继承标准化播放进度，Idle/Run 互切从头播放。方向是本地表现结果，不进入 `EEnemyState`、事件协议或网络复制。
- Mass 边界：Actor 后端读取 Character 速度；Mass 后端以后读取速度 Fragment 与本地观察者向量，复用九槽数据语义，不为每个实体创建 PaperFlipbookComponent。

## ADR-024：基本敌人采用逻辑胶囊接触伤害

- 状态：Accepted
- 决策：基本敌人不执行前摇/生效/收招攻击阶段。双方直立逻辑胶囊表面进入配置容差后进入 `ReadyToAttack`，首次立即伤害，随后按每敌人独立间隔重复伤害；脱离使用更大的容差形成滞回。
- 判定边界：MoveTo 的 `Reached` 只代表路径执行结果，不能直接造成伤害。接触必须通过后端中立胶囊距离计算，并由 `CombatTrace` 确认中间没有世界阻挡。最终伤害统一提交 `FCombatDamageRequest`。
- 不采用：不增加每 Actor 接触触发组件，不依赖 `BeginOverlap` 或持续接触时不稳定的 `OnHit`，不在敌人 Actor Tick 中维护计时器。
- 冷却规则：脱离不会重置下一次允许伤害时间，卡顿后不补发历史节拍。当前多个敌人独立叠加伤害，不预设玩家全局无敌时间。
- Mass 边界：Archetype 接触配置进入 Const Shared Fragment；身体、当前目标、接触状态和下一伤害时间进入实体 Fragment；空间查询 Processor 替换 Actor 胶囊与导航执行器，但伤害协议不变。

## ADR-025：敌人受击由统一冲量协议驱动，尸体使用独立碰撞和双材质阶段

- 状态：Accepted
- 决策：伤害源只通过 `FCombatDamageRequest.Impulse` 提供位移建议；目标 Archetype 决定普通打断、伤害比例/重击标签硬直、抗连续硬直窗口和致死倍率。Actor 后端使用 CharacterMovement/LaunchCharacter，不直接移动 Actor。
- 死亡流程：致死瞬间进入循环配置的 Death Flipbook，并闪红、真实击飞和逐黑；落地后停留并平滑淡出，再通过 EnemySubsystem 的统一退役点销毁或未来回收。
- 碰撞：死亡胶囊切到 `EnemyCorpse`；项目通道默认响应为 Block 以满足地面/场景组件的双向阻挡，尸体自身只阻挡 `WorldStatic`、`WorldDynamic` 和其他尸体，忽略 Pawn 与 CombatTrace。尸体不可作为角色行走基底；活敌人踩头属于后续独立规则。
- 表现：非致死击飞/硬直期间暂停速度方向判定并固定使用 `TowardViewer Idle`；死亡仍立即进入独立 Death Flipbook。
- 材质：项目维护一个存活 Masked 父材质和一个死亡 Translucent 父材质，DreamShader `.dsm` 为真源。共享 MIC 可调整普通/致死闪色、峰值覆盖、逐黑颜色、亮度和死亡不透明度；表现组件以 Custom Primitive Data 驱动每敌人的时间进度，不叠加第二个纸片组件，不为每敌人创建 MID。
- 理由：把伤害规则、Actor 物理执行和纸片表现拆开，当前能获得明确命中反馈与尸体空间感，后续 Mass 可以把同一冲量/状态数据映射为 Fragment 和实例自定义数据。
- 代价：死亡阶段会产生有限的 Translucent 过绘；大量尸体时应由敌潮预算、LOD 或更短寿命控制，而不是让所有存活敌人长期使用 Translucent。

## ADR-017：Lyra 仅作选择性参考，不作为工程基底

- 状态：Accepted
- 决策：不采用 Lyra 作为工程基底，不引入 GameFeatures / ModularGameplay / Experience / GAS 全栈；仅选择性参考其 CommonUI 输入与 UI 栈、装备/武器组织、Pawn 数据驱动与输入上下文模式。
- 理由：Lyra 面向大型多项目团队，重仓 GAS + 模块化，与我们的 Mass 敌潮、自研增量系统、自定义批次快照联机路线冲突；直接照搬会显著拖慢开发。
- 代价：需要的参考模式需自行按需抽取实现，不整体依赖 Lyra。
