# 技术设计文档（TDD）

> 引擎：Unreal Engine 5.8（C++ 为主，蓝图负责内容与 UI 组装）  
> 版本：v0.2（实现同步版）  
> 日期：2026-08-19  
> 关联文档：[02-游戏设计文档](./02-游戏设计文档.md)、[05-开发路线图](./05-开发路线图.md)、[06-设计决策记录](./06-设计决策记录.md)、[future/04-联机方案](./future/04-联机方案.md)

## 1. 目标与约束

### 1.1 性能目标（初始指标，M1 实测后校准）

| 场景 | 目标 |
|---|---|
| 单机 | 同屏 3000+ 敌人，1080p / 60 FPS（GTX 1050 级最低档可 30 FPS） |
| 联机客户端 | 同屏 1500+ 敌人（4 人时怪物总量按人数缩放，客户端只渲染近处完整个体） |
| 游戏线程预算 | ≤ 8 ms/帧 |
| 渲染线程/GPU 预算 | ≤ 10 ms/帧 |
| 内存 | 8 GB 可运行，纹理池/粒子池有上限控制 |

### 1.2 技术原则

1. **C++ 核心、数据驱动内容**：玩法逻辑走 C++，武器/敌人/Perk/设施走 DataAsset/DataTable，蓝图只做组合与表现。
2. **联机优先的架构习惯**：即使写单机功能，也默认服务器权威、客户端预测的边界清晰（避免后期返工）。
3. **先跑通，再抽象**：MVP 阶段保持单模块；当目录依赖边界清晰后再拆模块/插件。
4. **可测量**：关键系统（敌潮、网络、建造、GC）从 M1 起就有 stat/日志/自动化测试。

## 2. 技术选型

| 领域 | 选型 | 理由 |
|---|---|---|
| 输入 | Enhanced Input（已启用） | 标准、支持键鼠/手柄、上下文切换 |
| 大群 AI | Mass Entity（MassEntity / MassSpawner / MassRepresentation / MassNavigation） | 千级实体的标准方案；避免数千 AIController |
| 精英/BOSS AI | StateTree / GameplayStateTree（已启用） | 少量高复杂度行为用状态树，逻辑可读 |
| 大规模渲染 | ISM / HISM + MassRepresentation | 千级实例合批渲染 |
| 特效 | Niagara | 枪口火光、命中、尸体碎片、环境 |
| 属性/Perk | 自研轻量数据驱动属性系统（v1）；预留 GAS 接口 | 避免过早引入 GAS 复杂度；M2 状态/主动技变复杂时再局部评估（见 ADR-006） |
| 数据 | UDataAsset / UDataTable / UPrimaryDataAsset / GameplayTags | 内容与逻辑解耦、平衡可配置 |
| UI | CommonUI（交互）+ UMG（HUD） | 菜单/按钮/焦点统一；战斗 HUD 保持轻量 |
| 存档 | USaveGame + 版本化序列化 | 引擎标准、稳定 |
| 联机会话 | OnlineSubsystem Steam（首发）；EOS 评估 | PC 首发 Steam；EOS 为后续跨平台留口 |
| 调试 | 自定义 Log 分类、Visual Logger、stat 组、Unreal Insights | 敌潮与网络问题必须有可观测性 |
| 自动化测试 | FAutomationTest / 功能测试 Actor | 数值、存档、网络逻辑可回归 |

> 参考说明：Lyra（Epic 示例工程）仅作选择性参考（CommonUI 输入/UI 栈、装备组织、Pawn 数据驱动），不作为工程基底（ADR-017）。

## 3. 模块与目录结构

### 3.1 当前工程状态

项目由 UE 5.8 First Person 模板创建，目前仍是单模块工程，但玩家、武器和正式敌人基础框架已经开始替换模板逻辑：

- Runtime 模块为 `GobulinGame`，Editor 模块为 `GobulinGameEditor`。
- Runtime 依赖包含 Enhanced Input、AI、StateTree、Mass、Niagara、CommonUI、GameplayTags、UMG 和 Slate。
- 当前玩家类为 `AGobulinPlayerCharacter`，玩家控制器为 `AGobulinPlayerController`。
- 当前玩家战斗反馈由原生 `UGobulinPlayerStatusWidget` 提供；正式 UI 可通过其蓝图子类替换表现。
- 当前正式玩家武器为 `UGobulinSwordCombatComponent` + `UGobulinWeaponViewComponent`。
- 当前正式敌人由 `UGobulinEnemySubsystem` 管理，Actor 后端为 `AGobulinEnemyActor`；旧 Demo 类不再作为正式路径。
- GameMode 仍由模板蓝图配置，尚未切换到正式游戏模式。

### 3.2 规划目录结构（单模块阶段）

```
Source/GobulinGame/
  Core/          # 框架类、子系统、公共工具
  Combat/        # 玩家武器、命中、属性和战斗反馈
  Player/        # 玩家角色、控制器、相机反馈
  Enemy/         # 正式敌人角色、数据和动画状态
  Horde/         # Mass 敌潮、生成器、空间查询、事件流
  Base/          # 魔王城、地块、建筑、炮塔、魔王军
  Meta/          # 货币、转生头衔、图纸、转生深度、存档
  Net/           # 会话、加入/离开、快照通道、重连
  Data/          # DataAsset/DataTable/GameplayTags 定义与加载
  UI/            # HUD、菜单、结算、建造 UI
  AI/            # 精英/BOSS StateTree、Nav 辅助
```

拆分模块的时机：M4 联机完成后，若 `Horde` 与 `Net` 的依赖边界已稳定，拆为独立模块（如 `GobulinHorde`、`GobulinNet`）以缩短编译时间与强化边界。过早拆分会增加样板代码，收益低。

| 子系统 | 类型 | 职责 |
|---|---|---|
| `USessionManager` | UGameInstanceSubsystem | 创建/加入会话、邀请、玩家档案加载 |
| `UHordeDirector` | UWorldSubsystem | 勇者潮生成调度、悬赏等级、Mass 生成队列 |

### 4.3 关键接口

- `ICombatantEndpoint`：当前 Actor 后端统一伤害端点，战斗调用方只持有 `FCombatantHandle`。
- `UCombatantRegistrySubsystem`：维护句柄、Actor 适配映射以及队伍/位置/逻辑胶囊/存活快照。
- `UBattleAttributeComponent`：运行时属性容器；当前使用 `BattleTag_Health_Current`、`BattleTag_Health_Max` 和 `BattleTag_Movement_Speed`。
- `UGobulinHitStopSubsystem`：有效命中后的全局 Hit Stop 处理。
- `IBuildable`：建筑蓝图定义、地块尺寸、建造/拆除接口。
- `UGameEventBus`（World 级）：局内事件（击杀、掉落、建造、悬赏）的低耦合发布/订阅；联机时事件由 Net 层序列化为事件流。

## 5. 海量敌人方案（Horde）

这是本作的长期性能目标，不是当前正式敌人基础框架的前置条件。M1 先用少量完整 Actor 验证战斗和纸片表现，再建立 Mass 敌潮探针。

### 5.1 架构

- **规模化目标**：每只杂兵是 Mass 实体（Entity），由 Processor 驱动（移动、朝向、攻击、生命周期）。
- **不创建 AIController**：杂兵没有独立 Controller/Pawn；行为用轻量 Fragment + Processor（冲锋、绕障、攻击节奏）。
- **渲染**：杂兵用 2D 纸片精灵（面向相机四边形 + 材质翻页动画，MassRepresentation 实例化）；按距离降帧/降清晰度，远距离仅显示剪影。
- **碰撞/命中**：玩家射击不依赖逐实体碰撞体；用空间哈希网格（Spatial Hash）查询射线经过区域内的实体，再对命中实体做简单胶囊判定；伤害通过 Mass 信号/事件进入实体 Fragment。
- **寻路**：基地地图小、路线相对固定；用 Flow Field（离线/低成本更新）为主 + MassNavigation 回避（Avoidance）处理近距碰撞；精英/BOSS 用 NavMesh + StateTree。
- **当前原型**：`UGobulinEnemySubsystem` 低频索敌并生成后端中立移动意图；`AGobulinEnemyActor + AGobulinEnemyAIController` 使用 NavMesh/CharacterMovement 执行。Controller 不持有行为树或玩法决策。
- **怪潮堆积原型**：存活敌人使用 `EnemyBody` 通道并忽略彼此刚体碰撞；EnemySubsystem 以三维局部网格统计虚拟粒子密度，以 CharacterMovement 输入执行水平推进/分离，并把后排压力转换为受限的向上速度。NavMesh 完整路径只作为候选：PathFollowing 阻塞，或落地 Character 在 `Moving` 中持续没有取得目标距离进展时，Subsystem 会否决路径并进入 `CrowdPushing`。被否决路径只有在敌人高度、目标位置或目标距离发生足够变化后，才允许按句柄错峰做只读完整路径探测；探测失败不清空速度，Falling 期间暂停探测，成立后才重新提交 MoveTo。Actor 基础敌人使用 `UGobulinEnemyMovementComponent`，始终允许走下边缘，并以脚底中心附近的小半径地面扫描决定是否继续 Walking；中心失去支撑或下方落差超过吸附阈值时，在同一次移动更新中进入 Falling，不再沿边寻找替代方向，也不再探测预定安全落点。普通世界物体可在足够局部压力下被越过；真正不可进入或不可跌落的区域由空气墙或 `EnemySwarmBoundary` 明确阻挡。
- **基础攻击**：最小杂兵以双方逻辑胶囊表面接触作为伤害条件，CombatTrace 只负责排除中间世界遮挡；每敌人维护独立伤害节拍，不创建 Overlap 触发组件。Mass 阶段改为空间查询 Processor，继续提交同一伤害协议。
- **受击规则**：伤害请求携带后端中立 Impulse；普通命中进入短打断，重击标签或单次伤害比例阈值进入带免疫窗的硬直。Actor 后端用 CharacterMovement 执行，并在非致死击飞/硬直期间固定使用面向玩家 Idle；Mass 后端以后转换为速度 Fragment/受击 Processor。
- **死亡规则**：致死伤害立即失活战斗快照，进入循环 Death、红闪和击飞；尸体使用专用 `EnemyCorpse` 通道，仅阻挡世界和其他尸体，落地后停留、淡出并从统一退役点回收。
- **BOSS/精英目标**：数量少（几十只），使用完整 Actor 或带 Controller 的 Mass 实体 + StateTree，参与常规复制。
- **Mass 迁移边界**：`FGobulinEnemyCrowdDefinition` 进入 Const Shared Fragment，局部邻居数/压力进入实体 Fragment；Processor 复用同一网格与压力语义，但不创建 ACharacter。当前 Actor 第一轮仍让根胶囊兼任世界/玩家/战斗身体，第二轮先拆分这项职责再做规模探针。

### 5.2 生成

- `UHordeDirector` 根据悬赏等级、玩家数、转生深度生成波次配方（SpawnData DataAsset）。
- 生成位置：地图边缘的固定入口 + 悬赏触发的「勇者涌入口」。
- 生成采用预算队列：每帧最多生成 N 只（如 200/帧），避免瞬时卡顿。

### 5.3 生命周期与回收

- 死亡 → 伤害数字/击杀事件入队 → 实体归还 Entity 池（Mass 复用）→ 尸体用 Niagara/ISM 临时表现，不保留数千具尸体物理体。
- 掉落物：不是每只怪一个 Actor；掉落以「掉落簇」形式存在（金币堆、弹药箱），由事件流生成并复用池。

### 5.4 联机下的敌潮

详见 [future/04-联机方案.md](./future/04-联机方案.md) 第 4 节。核心思路：

- 服务器权威模拟全部敌潮；
- 客户端通过「批次快照 + 确定性位置 + 事件流」重建可见敌潮；
- 客户端看到的个体与服务器实体弱绑定（视觉代理），关键交互（击杀/掉落/伤害）以事件确认。

### 5.5 2D 纸片角色渲染（美术方案的工程落点）

美术方向为「3D 低模场景 + 全 2D 纸片角色」，技术落点如下：

- **角色表现**：Actor 原型使用 Paper2D Flipbook 作为可编辑的内容制作源；运行时纸片水平面向相机，不建骨骼网格。
- **海量勇者潮**：杂兵使用统一的精灵图集 + 每实例动画帧偏移（Per-Instance Custom Data），配合 MassRepresentation 实例化；数量不依赖骨骼动画预算。
- **方向感**：基本杂兵始终面向相机，并根据实际水平速度相对本地观察者选择前/后/屏幕左/屏幕右四方向 Idle 或 Run；精英/BOSS 后续可扩展 8 方向或独立动作资源。
- **阴影**：统一使用预烘焙贴花假阴影（Blob Shadow），不做逐角色实时投影，避免纸片浮空感。
- **玩家手部**：第一人称武器与手臂使用 2D FPS 武器贴图层（Overlay），与 2D 角色风格统一；若手感验证不佳，再评估 3D 手部 + 2D 武器贴图混合。
- **性能与内存**：精灵图集按敌人类型分页，纹理 Streaming 控制显存；低画质档位降低动画帧率与精灵分辨率。
- **验证点（M1）**：必须在原型期验证「面向相机精灵在 FPS 下的可读性」「3000 个动画精灵的合批成本」「BOSS 8 方向帧的观感」。

具体管线（ADR-020）：

- **编辑源**：每个语义状态直接引用原生 `UPaperFlipbook`，帧、帧率、Sprite 和默认材质在 Paper2D 编辑器中维护。
- **方向策略**：当前基本杂兵使用相对本地观察者的四方向 Idle/Run 资源并水平面向相机；方向由实际速度选择，只属于本地表现，不写入权威敌人状态。
- **底层实现类**：`UGobulinEnemyPresentationComponent` 继承 `UPaperFlipbookComponent`，挂在胶囊底部的 `FeetAnchor` 下。
- **正式敌人状态层**：`UGobulinEnemyArchetype` 为基本敌人保存四方向 `Idle`、四方向 `Run` 和 `Death` 九个槽；`UGobulinEnemySubsystem` 推进玩法状态，Actor 表现适配器根据状态和速度选择资源；旧 Demo 类不作为正式敌人基类。
- **敌人材质**：存活与死亡分别使用项目自有 Masked/Translucent Paper2D 父材质；死亡 Translucent 材质以 Masked 方式参与动态阴影，使存活与尸体阶段统一服从 Archetype 的 `bCastShadow`。普通/致死闪色、峰值覆盖、逐黑颜色、亮度和死亡不透明度可由共享材质实例调整，每敌人的闪色、逐黑与淡出时间数据由 Custom Primitive Data 驱动，不创建每敌人 MID。DreamShader `.dsm` 是父材质图真源。
- **编辑器装配**：`AGobulinEnemyPreviewActor` 负责视口预览与白名单烘焙，不进入 Cook，不参与运行时句柄注册。
- **Mass 转换**：Paper2D 不作为千级敌潮的一实体一组件方案；Mass 阶段从同一 Archetype 转换共享动画/渲染数据并交给实例表现后端。
- **角色分层**：基本杂兵使用完整四方向 Idle/Run 加死亡；玩家/队友/NPC 与 BOSS 的方向数量和动作资源后续按可读性、内容成本分别确定。
- **团队识别**：玩家阵营统一描边 + 头顶名牌；敌人不描边或使用另一套色系，保证联机中一眼区分。
- **第一人称**：本地武器用相机挂载的 2D Plane 贴图层（`UGobulinWeaponViewComponent`），由 `UGobulinSwordCombatComponent` 推进攻击时间，并用位置/旋转曲线驱动变换；武器层仅本地可见、不参与联机复制。

## 6. 战斗与武器系统

### 6.1 当前剑系统

- `UGobulinSwordDefinition` 是当前第一把武器的数据资产。
- `UGobulinSwordCombatComponent` 管理攻击状态、输入缓存、按住左键自动连击、剑尖轨迹检测和 `FDamageInfo` 派发。
- `UGobulinWeaponViewComponent` 挂载到第一人称相机，使用 Plane 显示贴图。
- 攻击位置和旋转由 `UCurveVector` 驱动，不使用武器 Flipbook、手部模型或旧 W01/W03/W05 体系。
- `UGobulinSwordFeedbackComponent` 负责挥剑音效、命中音效、相机震动和 Hit Stop。

### 6.2 后续通用武器系统

后续远程武器、投射物、弹药和 Tier 曲线仍可使用独立 DataAsset，但不能覆盖当前剑系统的实现事实。新增武器先抽取稳定的通用接口，再决定是否引入 `UWeaponDefinition`、弹药组件和武器切换系统。

### 6.3 命中与联机边界

当前剑的命中检测为本地原型流程；正式联机阶段再按 [future/04-联机方案.md](./future/04-联机方案.md) 将伤害结算迁移到服务器权威路径。当前不提前实现完整回溯或客户端预测伤害。

## 7. 属性与 Perk（轻量自研）

### 7.1 结构

- `UBattleAttributeComponent`：挂在角色上的运行时属性容器，内部持有 `UBattleAttributeSet`。
- `UBattleAttributeSet`：当前保存属性值和变化委托；现阶段先覆盖生命和移动速度。
- 修改器（`FAttributeModifier`）：来源（Perk/武器 Mod/设施/临时 Buff）+ 目标属性 + 加算/乘算 + 持续时间。
- 修改器堆叠规则用 GameplayTags 控制（如 `Modifier.BulletDamage` 的叠加上限）。
- 通过 `GetAttributeValue(AttributeTag)` 查询；属性变化时广播事件驱动角色移动等表现。

### 7.2 为什么暂不引入 GAS

- GAS 适合大量技能/状态/网络效果的复杂游戏；本作 v1 的 Perk 以静态加成与少量主动技为主，自研系统足以覆盖。
- GAS 的学习/调试成本高，会拖慢 M1 垂直切片。
- GAS 面向 Actor/AbilitySystemComponent，不适合覆盖千人 Mass 敌潮的伤害结算；敌潮伤害始终走 Mass 自研系统。
- 预留迁移路径：属性读取走统一接口；若 M2 主动技/状态效果复杂度显著上升，再评估只给玩家侧局部引入 GAS（见 ADR-006）。

## 8. 基地系统

### 8.1 数据

- 每个设施/防御件一个 `UBuildingDefinition`（DataAsset）：占地、耐久、费用、等级上限、升级表、功能组件引用。
- 地块：`APlotActor` 网格节点，记录占用/归属；建造合法性由 `UBuildingManager` 服务器校验。

### 8.2 运行

- 局外设施：永久存在于基地地图，等级存世界存档。
- 局内临时防御：夜晚开始时按「蓝图配方 + 预算」放置，天亮销毁；放置过程服务器权威、客户端预览。
- 魔王军：魔池生成 `AMinionUnit`（少量 Actor，几十个），用简单行为树/StateTree 驻守与跟随标记点。

## 9. 存档系统

### 9.1 两类存档

| 存档 | 属主 | 内容 | 写入时机 |
|---|---|---|---|
| 玩家档案 `UMetaSave` | 本地玩家（Steam ID） | 金币/魔核/冥银/图纸/转生头衔/转生深度/已解锁内容 | 每次结算、购买后 |
| 世界存档 `UWorldSave` | 房主 | 基地设施等级、地块、魔王军上限、NPC 状态、剧情标记 | 夜与夜之间、手动保存 |

### 9.2 版本化

- 两个存档都有 `Version` 字段与迁移函数；加载时校验版本并迁移，坏档回退到最近有效版本。
- 联机世界存档随房主；玩家档案随个人（联机中获得的个人货币写入本地档案）。
- 反作弊：服务器对玩家提交的档案做范围校验（数值上限、解锁校验），不信任客户端原始数据（正式版评估 EOS 云存档）。

## 11. 性能预算与优化计划

| 方向 | 手段 |
|---|---|
| 游戏线程 | Mass Processor 分帧、实体池、避免每实体 Tick；掉落/死亡事件批量处理 |
| 渲染 | HISM 合批、LOD、远距离减面、粒子池、尸体即时回收 |
| 2D 精灵 | 精灵四边形合批、材质翻页动画、按距离降帧播放、描边贴图预烘焙 |
| 内存 | 纹理 Streaming、Niagara Pool、实体 Fragment 紧凑布局 |
| GC | 运行时避免每帧 NewObject；可池化对象复用 |
| 网络 | 批次快照 + 压缩位流、事件合并、复制剔除（按距离/可见性） |
| 加载 | 分 PIE/Shipping 预加载关键 DataAsset；夜晚切换用软引用 + 异步加载 |

## 12. 测试策略

### 12.1 自动化

- 数值测试：武器 Tier/Perk/货币换算用 FAutomationTest 断言曲线预期。
- 存档测试：写入→迁移→读取→坏档回退。
- 建造测试：地块合法性、预算扣减、权限。
- 网络测试（M4 后）：PIE 多进程模拟 2/4 人，验证共享状态与事件流一致性。

### 12.2 性能测试

- 标准场景：固定波次配方、固定时间线，跑 `stat unit` 与 Unreal Insights 记录基线。
- 敌潮压力场景：3000 敌人 + 全屏特效，检查最低帧率与卡顿尖峰。
- 联机压力：4 客户端 + 模拟 100-300ms RTT 与 3% 丢包，验证可玩性。

### 12.3 功能测试

- 关卡中放置 AFunctionalTest 节点：发布悬赏→波次断言、建造→拆除断言、结算→货币断言。
