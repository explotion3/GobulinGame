# 技术设计文档（TDD）

> 引擎：Unreal Engine 5.8（C++ 为主，蓝图负责内容与 UI 组装）  
> 版本：v0.1（规划稿）  
> 日期：2026-08-09  
> 关联文档：[02-游戏设计文档](./02-游戏设计文档.md)、[04-联机方案](./04-联机方案.md)、[06-设计决策记录](./06-设计决策记录.md)

## 1. 目标与约束

### 1.1 性能目标（初始指标，M1 实测后校准）

| 场景 | 目标 |
|---|---|
| 单机 | 同屏 3000+ 敌人，1080p / 60 FPS（GTX 1050 级最低档可 30 FPS） |
| 联机客户端 | 同屏 1500+ 敌人（4 人时怪物总量按人数缩放，客户端只渲染近处完整个体） |
| 游戏线程预算 | ≤ 8 ms/帧 |
| 渲染线程/GPU 预算 | ≤ 10 ms/帧 |
| 内存 | 8 GB 可运行，纹理池/粒子池有上限控制 |

### 1.2 技术原则

1. **C++ 核心、数据驱动内容**：玩法逻辑走 C++，武器/敌人/Perk/设施走 DataAsset/DataTable，蓝图只做组合与表现。
2. **联机优先的架构习惯**：即使写单机功能，也默认服务器权威、客户端预测的边界清晰（避免后期返工）。
3. **先跑通，再抽象**：MVP 阶段保持单模块；当目录依赖边界清晰后再拆模块/插件。
4. **可测量**：关键系统（敌潮、网络、建造、GC）从 M1 起就有 stat/日志/自动化测试。

## 2. 技术选型

| 领域 | 选型 | 理由 |
|---|---|---|
| 输入 | Enhanced Input（已启用） | 标准、支持键鼠/手柄、上下文切换 |
| 大群 AI | Mass Entity（MassEntity / MassSpawner / MassRepresentation / MassNavigation） | 千级实体的标准方案；避免数千 AIController |
| 精英/BOSS AI | StateTree / GameplayStateTree（已启用） | 少量高复杂度行为用状态树，逻辑可读 |
| 大规模渲染 | ISM / HISM + MassRepresentation | 千级实例合批渲染 |
| 特效 | Niagara | 枪口火光、命中、尸体碎片、环境 |
| 属性/Perk | 自研轻量数据驱动属性系统（v1）；预留 GAS 接口 | 避免过早引入 GAS 复杂度；M2 状态/主动技变复杂时再局部评估（见 ADR-006） |
| 数据 | UDataAsset / UDataTable / UPrimaryDataAsset / GameplayTags | 内容与逻辑解耦、平衡可配置 |
| UI | CommonUI（交互）+ UMG（HUD） | 菜单/按钮/焦点统一；战斗 HUD 保持轻量 |
| 存档 | USaveGame + 版本化序列化 | 引擎标准、稳定 |
| 联机会话 | OnlineSubsystem Steam（首发）；EOS 评估 | PC 首发 Steam；EOS 为后续跨平台留口 |
| 调试 | 自定义 Log 分类、Visual Logger、stat 组、Unreal Insights | 敌潮与网络问题必须有可观测性 |
| 自动化测试 | FAutomationTest / 功能测试 Actor | 数值、存档、网络逻辑可回归 |

> 参考说明：Lyra（Epic 示例工程）仅作选择性参考（CommonUI 输入/UI 栈、装备组织、Pawn 数据驱动），不作为工程基底（ADR-017）。

## 3. 模块与目录结构

### 3.1 当前工程状态

项目由 UE 5.8 First Person 模板创建：

- 单模块 `GobulinGame`（Runtime），已依赖：Core、CoreUObject、Engine、InputCore、EnhancedInput、AIModule、StateTreeModule、GameplayStateTreeModule、UMG、Slate。
- 已启用插件：ModelingToolsEditorMode（编辑器）、StateTree、GameplayStateTree。
- 已有模板类：`GobulinGameCharacter`、`GobulinGamePlayerController`、`GobulinGameGameMode`、`GobulinGameCameraManager`。

### 3.2 规划目录结构（单模块阶段）

```
Source/GobulinGame/
  Core/          # 框架类、子系统、公共工具
  Combat/        # 玩家、武器、弹药、命中、Perk、属性
  Horde/         # Mass 敌潮、生成器、空间查询、事件流
  Base/          # 魔王城、地块、建筑、炮塔、魔王军
  Meta/          # 货币、转生头衔、图纸、转生深度、存档
  Net/           # 会话、加入/离开、快照通道、重连
  Data/          # DataAsset/DataTable/GameplayTags 定义与加载
  UI/            # HUD、菜单、结算、建造 UI
  AI/            # 精英/BOSS StateTree、Nav 辅助
```

拆分模块的时机：M4 联机完成后，若 `Horde` 与 `Net` 的依赖边界已稳定，拆为独立模块（如 `GobulinHorde`、`GobulinNet`）以缩短编译时间与强化边界。过早拆分会增加样板代码，收益低。

### 4.3 关键接口

- `IDamageable`：所有可伤害实体（勇者潮、建筑、BOSS、魔王殿）实现；统一伤害、状态、死亡事件。
- `IBuildable`：建筑蓝图定义、地块尺寸、建造/拆除接口。
- `UGameEventBus`（World 级）：局内事件（击杀、掉落、建造、悬赏）的低耦合发布/订阅；联机时事件由 Net 层序列化为事件流。

## 5. 海量敌人方案（Horde）

这是本作最大的技术风险，M1 必须先验证。

### 5.1 架构

- **Mass Entity 模拟**：每只杂兵是 Mass 实体（Entity），由 Processor 驱动（移动、朝向、攻击、生命周期）。
- **不创建 AIController**：杂兵没有独立 Controller/Pawn；行为用轻量 Fragment + Processor（冲锋、绕障、攻击节奏）。
- **渲染**：杂兵用 2D 纸片精灵（面向相机四边形 + 材质翻页动画，MassRepresentation 实例化）；按距离降帧/降清晰度，远距离仅显示剪影。
- **碰撞/命中**：玩家射击不依赖逐实体碰撞体；用空间哈希网格（Spatial Hash）查询射线经过区域内的实体，再对命中实体做简单胶囊判定；伤害通过 Mass 信号/事件进入实体 Fragment。
- **寻路**：基地地图小、路线相对固定；用 Flow Field（离线/低成本更新）为主 + MassNavigation 回避（Avoidance）处理近距碰撞；精英/BOSS 用 NavMesh + StateTree。
- **BOSS/精英**：数量少（几十只），用完整 Actor 或带 Controller 的 Mass 实体 + StateTree，参与常规复制。

### 5.2 生成

- `UHordeDirector` 根据悬赏等级、玩家数、转生深度生成波次配方（SpawnData DataAsset）。
- 生成位置：地图边缘的固定入口 + 悬赏触发的「勇者涌入口」。
- 生成采用预算队列：每帧最多生成 N 只（如 200/帧），避免瞬时卡顿。

### 5.3 生命周期与回收

- 死亡 → 伤害数字/击杀事件入队 → 实体归还 Entity 池（Mass 复用）→ 尸体用 Niagara/ISM 临时表现，不保留数千具尸体物理体。
- 掉落物：不是每只怪一个 Actor；掉落以「掉落簇」形式存在（金币堆、弹药箱），由事件流生成并复用池。

### 5.4 联机下的敌潮

详见 [04-联机方案.md](./04-联机方案.md) 第 4 节。核心思路：

- 服务器权威模拟全部敌潮；
- 客户端通过「批次快照 + 确定性位置 + 事件流」重建可见敌潮；
- 客户端看到的个体与服务器实体弱绑定（视觉代理），关键交互（击杀/掉落/伤害）以事件确认。

### 5.5 2D 纸片角色渲染（美术方案的工程落点）

美术方向为「3D 低模场景 + 全 2D 纸片角色」，技术落点如下：

- **角色表现**：每个角色是一个面向相机的四边形（Billboard Quad），动画用材质驱动的翻页（Flipbook）播放序列帧；不建骨骼网格，降低动画与渲染成本。
- **海量勇者潮**：杂兵使用统一的精灵图集 + 每实例动画帧偏移（Per-Instance Custom Data），配合 MassRepresentation 实例化；数量不依赖骨骼动画预算。
- **方向感**：普通杂兵始终面向相机（配合描边与剪影保证可读）；精英/BOSS 使用 8 方向帧（或 4 方向 + 翻转），避免「纸片转侧成一条线」。
- **阴影**：统一使用预烘焙贴花假阴影（Blob Shadow），不做逐角色实时投影，避免纸片浮空感。
- **玩家手部**：第一人称武器与手臂使用 2D FPS 武器贴图层（Overlay），与 2D 角色风格统一；若手感验证不佳，再评估 3D 手部 + 2D 武器贴图混合。
- **性能与内存**：精灵图集按敌人类型分页，纹理 Streaming 控制显存；低画质档位降低动画帧率与精灵分辨率。
- **验证点（M1）**：必须在原型期验证「面向相机精灵在 FPS 下的可读性」「3000 个动画精灵的合批成本」「BOSS 8 方向帧的观感」。

具体管线（ADR-016）：

- **图集与 Clip**：每敌人一张图集，行 = 方向、列 = 帧；`FSpriteClip` 定义 Idle/Move/Attack/Hurt/Death 等片段及循环/帧率。
- **方向策略**：杂兵 1 方向（始终面向相机）；精英/BOSS/NPC 用 8 方向（4 方向绘制 + 水平镜像）；由动画控制器按相机夹角选择方向行。
- **实现类**：`USpriteFlipbook`（图集资产）、`USpriteBillboardComponent`（面向相机四边形 + 帧播放）、`USpriteAnimatorComponent`（方向/状态驱动）。
- **角色分层**：杂兵 1 方向（面向相机）；玩家/队友/NPC 用 8 方向帧（4 方向绘制 + 水平镜像），方向随移动/瞄准切换；BOSS 用 8 方向高帧。
- **团队识别**：玩家阵营统一描边 + 头顶名牌；敌人不描边或使用另一套色系，保证联机中一眼区分。
- **第一人称**：本地武器用 2D 武器贴图层（`UFPSWeaponOverlayComponent` + `UFPSWeaponAnimator`），不把 3D AnimBP 作为主线；武器层仅本地可见、不参与联机复制。

## 6. 战斗与武器系统

### 6.1 命中判定

- **Hitscan 武器**：服务器执行射线追踪并结算伤害；客户端执行表现射线 + 命中特效预测（伤害结果以服务器为准）。
- **投射物武器**：弹药稀缺、可交互（爆炸/穿透）的武器使用复制的投射物 Actor；纯表现粒子不复制。
- **爆头/弱点**：命中子部位（如头部 Socket/区域）→ 伤害倍率；联机下由服务器射线判定，客户端显示暴击反馈。
- **服务器延迟补偿**：MVP 不做完整回溯（rewind）；用「容差命中」+ 延迟在 200ms 内的体验优化。联机后如有明显体感问题，再评估服务器回滚方案（见 ADR-008）。

### 6.2 武器数据

```
UWeaponDefinition : UPrimaryDataAsset
  - 基础属性：伤害、射速、弹匣、散布、后座曲线、距离衰减、穿透、弹种
  - 模式：全自动/半自动/蓄力/爆炸
  - Tier 曲线：UCurveTable（伤害/射速/换弹随 Tier 缩放）
  - Mod 插槽定义 + Mod 白名单
  - 表现引用：Mesh、Niagara、音效、动画
```

### 6.3 弹药补给

- 弹药掉落规则由武器 DataAsset 的 `AmmoDropRule` 定义（击杀何种敌人掉何种弹药），避免在角色代码里写死。
- 弹药上限：基础值 + Perk/基地加成，曲线受 GameplayTags 约束。

## 7. 属性与 Perk（轻量自研）

### 7.1 结构

- `UBattleAttributeSet`：复合结构（血量、护甲、伤害倍率、换弹速度、暴击等），作为 UObject 挂到角色/武器上下文。
- 修改器（`FAttributeModifier`）：来源（Perk/武器 Mod/设施/临时 Buff）+ 目标属性 + 加算/乘算 + 持续时间。
- 修改器堆叠规则用 GameplayTags 控制（如 `Modifier.BulletDamage` 的叠加上限）。
- 提供 `GetFinalValue(Attribute)` 查询；变化时广播事件驱动 HUD/武器表现。

### 7.2 为什么暂不引入 GAS

- GAS 适合大量技能/状态/网络效果的复杂游戏；本作 v1 的 Perk 以静态加成与少量主动技为主，自研系统足以覆盖。
- GAS 的学习/调试成本高，会拖慢 M1 垂直切片。
- GAS 面向 Actor/AbilitySystemComponent，不适合覆盖千人 Mass 敌潮的伤害结算；敌潮伤害始终走 Mass 自研系统。
- 预留迁移路径：属性读取走统一接口；若 M2 主动技/状态效果复杂度显著上升，再评估只给玩家侧局部引入 GAS（见 ADR-006）。

## 8. 基地系统

### 8.1 数据

- 每个设施/防御件一个 `UBuildingDefinition`（DataAsset）：占地、耐久、费用、等级上限、升级表、功能组件引用。
- 地块：`APlotActor` 网格节点，记录占用/归属；建造合法性由 `UBuildingManager` 服务器校验。

### 8.2 运行

- 局外设施：永久存在于基地地图，等级存世界存档。
- 局内临时防御：夜晚开始时按「蓝图配方 + 预算」放置，天亮销毁；放置过程服务器权威、客户端预览。
- 魔王军：魔池生成 `AMinionUnit`（少量 Actor，几十个），用简单行为树/StateTree 驻守与跟随标记点。

## 9. 存档系统

### 9.1 两类存档

| 存档 | 属主 | 内容 | 写入时机 |
|---|---|---|---|
| 玩家档案 `UMetaSave` | 本地玩家（Steam ID） | 金币/魔核/冥银/图纸/转生头衔/转生深度/已解锁内容 | 每次结算、购买后 |
| 世界存档 `UWorldSave` | 房主 | 基地设施等级、地块、魔王军上限、NPC 状态、剧情标记 | 夜与夜之间、手动保存 |

### 9.2 版本化

- 两个存档都有 `Version` 字段与迁移函数；加载时校验版本并迁移，坏档回退到最近有效版本。
- 联机世界存档随房主；玩家档案随个人（联机中获得的个人货币写入本地档案）。
- 反作弊：服务器对玩家提交的档案做范围校验（数值上限、解锁校验），不信任客户端原始数据（正式版评估 EOS 云存档）。

## 11. 性能预算与优化计划

| 方向 | 手段 |
|---|---|
| 游戏线程 | Mass Processor 分帧、实体池、避免每实体 Tick；掉落/死亡事件批量处理 |
| 渲染 | HISM 合批、LOD、远距离减面、粒子池、尸体即时回收 |
| 2D 精灵 | 精灵四边形合批、材质翻页动画、按距离降帧播放、描边贴图预烘焙 |
| 内存 | 纹理 Streaming、Niagara Pool、实体 Fragment 紧凑布局 |
| GC | 运行时避免每帧 NewObject；可池化对象复用 |
| 网络 | 批次快照 + 压缩位流、事件合并、复制剔除（按距离/可见性） |
| 加载 | 分 PIE/Shipping 预加载关键 DataAsset；夜晚切换用软引用 + 异步加载 |

## 12. 测试策略

### 12.1 自动化

- 数值测试：武器 Tier/Perk/货币换算用 FAutomationTest 断言曲线预期。
- 存档测试：写入→迁移→读取→坏档回退。
- 建造测试：地块合法性、预算扣减、权限。
- 网络测试（M4 后）：PIE 多进程模拟 2/4 人，验证共享状态与事件流一致性。

### 12.2 性能测试

- 标准场景：固定波次配方、固定时间线，跑 `stat unit` 与 Unreal Insights 记录基线。
- 敌潮压力场景：3000 敌人 + 全屏特效，检查最低帧率与卡顿尖峰。
- 联机压力：4 客户端 + 模拟 100-300ms RTT 与 3% 丢包，验证可玩性。

### 12.3 功能测试

- 关卡中放置 AFunctionalTest 节点：发布悬赏→波次断言、建造→拆除断言、结算→货币断言。
